# Cool Java

A hundred tricks, patterns and small implementations that make Java more fun, more expressive or just more surprising. Monads in plain Java, validators that tell you everything at once, phantom types that turn bugs into compile errors, lock-free stacks, a regex engine in 30 lines, bytecode generated at runtime, and puzzlers that will make you doubt `==` forever.

Every document covers **one topic** and contains a **complete program**. Each one was compiled and run with a real JDK, and the output shown in the doc was generated by that run, not typed in. See [Running the examples](#running-the-examples).

## How to read a doc

Every doc starts with a badge line:

* **Since** is the oldest Java release the main example compiles on (checked with `javac --release N`). *Preview* means you need `--enable-preview` on that exact release. *Incubator* means the API lives in a `jdk.incubator` module.
* **Level** is Beginner, Intermediate or Advanced.
* **Verdict** is an honest opinion, not a rating of how clever the trick is:
  * ✅ **Production**: use it in real code, today.
  * ⚠️ **Situational**: great in the right spot, a liability elsewhere. The doc says which is which.
  * 🧪 **Party trick**: learn it, enjoy it, show it to colleagues, keep it out of your codebase.

Then: the problem, the trick, a full runnable example with its real output, how it works, gotchas, when not to use it, related docs and sources.

## Running the examples

The examples need no build tool and no dependencies. Copy the program from a doc into a file named after its main class and use the source launcher:

```shell
java NotificationDemo.java
```

Examples target **JDK 25** (the current LTS) unless the badge says otherwise. Preview features are demonstrated on **JDK 27**:

```shell
java --enable-preview --source 27 Main.java
```

### Verifying the whole collection

`tools/verify.py` extracts every checked code block, compiles and runs it, and compares the output with the doc:

```shell
export JDK25_HOME=/path/to/jdk-25
export JDK27_HOME=/path/to/jdk-27
python3 tools/verify.py                  # verify every doc
python3 tools/verify.py --since FILE     # also check the "Since" badge with javac --release N
python3 tools/verify.py --update FILE    # regenerate output blocks after editing an example
```

The verifier understands these fenced block types:

| Info string | Meaning |
|---|---|
| `java run` | Complete program, run on JDK 25, stdout must match the next `text output` block |
| `java preview` | Same, on JDK 27 with `--enable-preview` |
| `java compile-fail` | Must be rejected by javac; the next `text compile-error` block holds the real message |
| `java` | A fragment for explanation, not checked |

Options such as `jdk=27`, `args="..."`, `stderr`, `exit=1` and `nondeterministic` are documented at the top of `tools/verify.py`. Blocks marked `nondeterministic` (timings, thread interleavings) are run and must succeed, but their output is a sample and is not compared.

Some docs also show shell sessions (`javap`, `jar`, multi-file launches, a shebang script). Those were run for real when the doc was written and their output pasted in, but `verify.py` does not rerun them.

`tools/index.py` rebuilds the index above from the docs' own headers and checks every relative link:

```shell
python3 tools/index.py           # rebuild the index
python3 tools/index.py --check   # lint only
```

### Building the website

The same Markdown is published as a static site. `tools/site.py` renders it with markdown-it (plain Jekyll would treat the `{{` in Java code as template syntax), and `.github/workflows/pages.yml` deploys it to GitHub Pages on every push to `main`:

```shell
pip install markdown-it-py mdit-py-plugins
python3 tools/site.py              # writes _site/
python3 -m http.server -d _site    # preview at http://localhost:8000
```

## Adding a doc

Copy the structure of any existing doc (for example [011 · Notification Pattern Validator](02-patterns/011-notification-validator.md)), keep the badge line format exactly, leave the output blocks empty, run `verify.py --update` on it, read what the program really printed, and make the prose agree with it. Then rebuild the index.
